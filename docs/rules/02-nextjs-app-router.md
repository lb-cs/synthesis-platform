# Next.js — App Router

Applies to: `app/**`, `components/**`, anything importing from `next/*`.

## Next has changed

This is **Next.js 16**. APIs, conventions, and file structure differ from what training
data assumes. Read the versioned guide in `node_modules/next/dist/docs/01-app/` before
writing code that touches routing, data fetching, caching, or metadata — an API that
existed two majors ago is not evidence it exists now. Heed deprecation notices.

Starting points: `01-getting-started/03-layouts-and-pages.md`,
`05-server-and-client-components.md`, `06-fetching-data.md`, `15-route-handlers.md`.

## Server and client components

Every file under `app/` and `components/` is a **server component** unless it opens with
`'use client'`. Add the directive only where the file needs state, effects, event
handlers, or browser APIs — and put it on the smallest leaf that needs it, never on a
page or layout just because one child is interactive.

`components/health-check.tsx` is the reference: the page stays a server component; the
one interactive card is the client boundary.

## Route files

- `page.tsx` / `layout.tsx` — `export default function`. Take props as
  `PageProps<'/route'>` / `LayoutProps<'/'>`; these globals are generated by
  `next typegen` (see 04)
- `route.ts` — one named export per HTTP method: `export function GET()`. Return
  `Response.json(...)`. Validate first, then call a function in `lib/` — the handler
  itself carries no logic (`docs/agents/code-style.md` §11)
- Links are `next/link`. A shadcn `Button` that should navigate takes
  `render={<Link href="…" />} nativeButton={false}` — see 03

## Data and errors

- Fetch on the server where you can; a client component fetches only what depends on
  user interaction
- `fetch` throws only on network failure — check `res.ok` before reading the body
- Expected failures are values a component renders (a `status` union in state), not
  thrown exceptions. Throw for programmer or config errors where crashing early is right,
  and let an `error.tsx` boundary catch render errors

## Environment

Only `NEXT_PUBLIC_*` variables reach the browser, and they are inlined at build time —
so they are public. Everything else is server-only. Local values live in `.env.local`
(gitignored); `.env.example` documents the keys with placeholder values. Never put a
secret behind the `NEXT_PUBLIC_` prefix.

## Generated files

`next dev` (and `next build`) write files you should not edit by hand:

- `next-env.d.ts` — gitignored, regenerated
- `.next/types/` — route types, regenerated by `next typegen`
- The `nextjs-agent-rules` block at the top of `AGENTS.md` — re-added on every `next dev`.
  Leave it in place and commit it; deleting it only recreates the diff
